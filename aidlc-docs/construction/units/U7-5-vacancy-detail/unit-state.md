## Scope

Define the baseline vacancy-detail flow so a single vacancy can be surfaced in stable detail form for later management and discovery contexts without collapsing applications, bookmarks, or matching behavior into the same unit.

## Out of Scope

Concrete frontend/backend implementation code, search filters, applications, bookmarks, matching logic, and requirement-tag editing behavior.

## Dependencies

Depends on the requirements, security, data-model, architecture, API, routing, state-management, vacancy-create, vacancy-edit, vacancy-delete, and vacancy-list baselines.

## Acceptance Criteria

The unit documents vacancy-detail behavior, stable detail states, and relationship to later search, application, and matching units without producing application code.

## Risks

If vacancy detail is underspecified here, later student search, applications, and matching units can drift into conflicting interpretations of vacancy fields, visibility, and active-state behavior.

## Open Questions

Exact management-versus-student detail variants, related-vacancy links, and richer supporting sections can be refined later as long as the baseline vacancy detail remains explicit and stable.
